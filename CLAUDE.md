## О проекте

Приложение для автоматизации формирования пакета экзаменационных документов в области **неразрушающего контроля сварных соединений** (ВИК, РК, УК и т.д.).

Сейчас процесс ручной: специалист выгружает файлы из ЭДО и руками правит в них информацию (ФИО, метод контроля, даты, состав комиссии и т.д.) для каждого экзаменуемого. Это медленно и подвержено ошибкам.

**Цель приложения:** пользователь один раз вводит параметры экзамена, прикладывает файлы, которые нужно трансформировать, — и на выходе получает готовый ZIP-архив с заполненными документами, с корректными именами файлов.

- Не используй сложные паттерны проектирования, если без них можно обойтись.
- Разбивай работу на **маленькие, изолированные, проверяемые шаги** — мне важно потом самой(му) разобраться в каждом куске и при необходимости поправить.
- Каждый модуль трансформации документа делаем **отдельно и независимо** от остальных — никакой "монолитной" логики, которая обрабатывает все типы документов сразу.
- После каждого этапа — короткое резюме: что сделано, как проверить, что дальше.

## Стек

- **Frontend:** React, CSS-модули, HTML
- **Backend:** Node.js, Express
- **Обработка документов:** LibreOffice (headless, через CLI/UNO API) — для трансформации .docx/.xlsx и конвертации
- **Архивация:** формирование ZIP на выходе

Сначала — локальная версия (запуск на localhost). Деплой на сервер — отдельная, более поздняя задача, сейчас не проектируем под него специально (но и не делаем явно недеплоябельных решений).

## Структура данных и библиотека заготовок

В проекте есть **библиотека заготовок**, организованная по методам контроля:

```
library/
  ВИК/        # Визуально-измерительный контроль
    *.docx    # заготовки для трансформации (с плейсхолдерами)
  РК/         # Радиографический контроль
    ...
  УК/         # Ультразвуковой контроль
    ...
  (и другие методы по мере необходимости)
```

Внутри папки метода два типа файлов:
1. **Заготовки (templates)** — в них есть плейсхолдеры, которые нужно заменить на введённые пользователем данные.
2. **Статичные файлы** — прикладываются в итоговый архив без изменений.

## Форма ввода данных (поля и порядок — см. также SESSION_PROMPTS.md)

1. Фамилия Имя Отчество
2. Метод контроля (select: ВИК / РК / УК / ...) + № образца
3. Дата экзамена
4. Комиссия — Председатель
5. Комиссия — Эксперт
6. Комиссия — Технический эксперт
7. Drag&drop зона для загрузки файлов (тех, что нужно трансформировать)
8. Кнопка «Сгенерировать»
9. Блок «Скачать архив»

## Именование выходных файлов

Формат имени итоговых файлов нужно зафиксировать отдельно (зависит от метода контроля и набора данных). **Договориться о точном шаблоне имени — отдельная задача**, не предполагать его самостоятельно без уточнения у пользователя.

## Принципы реализации (общие)

- Каждый тип документа (метод контроля + конкретная заготовка) обрабатывается своим отдельным модулем-трансформером на backend (например `transformers/vik-protocol.js`, `transformers/rk-act.js` и т.д.), с понятным входом (данные формы) и выходом (готовый файл).
- Трансформация через LibreOffice headless — выносим в отдельный сервисный модуль, который остальные трансформеры переиспользуют, а не дублируют вызовы.
- Backend сначала покрываем простыми ручными/скриптовыми тестами на одном-двух реальных примерах файлов, без сложных тестовых фреймворков на первом этапе.
- Frontend — простая форма без сложного state-менеджмента (useState достаточно), без лишних библиотек, пока не появится явная необходимость.
